# 模板撰写的最小数据标注

模板不应保存 SQL、表名、连接信息或完整 QuerySpec。模板只描述“这里要填一个确定指标”或“这里需要一段基于数据的文字”。

## 槽位只保留三种模式

```json
{"slot_key":"T03_R002_C05_P01","mode":"metric","metric_key":"task_progress.completed_count"}
```

```json
{"slot_key":"P4609","mode":"context","topic":"group_a.本期建设成效","instruction":"根据事实写一段总结"}
```

静态文字不生成槽位；`slot_key` 和 DOCX 定位信息由解析器自动生成，不由业务人员填写。

## 指标模式

`metric_key` 是唯一需要人工确认的精确数据引用。指标库中的指标负责维护：

- 对应 QuerySpec、输出字段、单位、粒度和期间规则
- 数据语义、空值规则和证据要求
- 查询涉及的表及其关联关系

模板不再重复 `source_key`、`domain`、`query_id`、`field`、`selector`。指标库通过当前能力授权的数据源解析这些信息。指标未定义时，槽位进入 `needs_confirmation`，不能猜 SQL。

## 上下文模式

叙述段落只标一个稳定的 `topic`，例如“专业群本期建设成效”或“资金执行情况”。运行时根据主题读取已授权的指标、任务和材料候选，形成事实上下文交给模型；模型负责组织语言，不负责把每个事实预先塞进模板。

上下文必须带 `evidence_refs`，正文中的数字只能来自这些事实。没有事实时生成留空/高亮或询问，不把候选记录数量当成果数量。

## 执行流程

1. DOCX 解析器生成结构槽位，并将明显的表头、标题和固定文字标为静态。
2. 只对数字、日期、比例和需事实支撑的段落生成待确认清单。
3. 标注人员为数值组选择 `metric_key`，为叙述组选择 `topic`；同组槽位可批量处理。
4. 运行时先按指标批量取数，再按主题组装写作上下文。
5. 渲染器只处理两类结果：指标值直接回填，主题上下文交给模型写作并保存证据。

## 对现有实现的调整方向

- `metrics.json` 成为模板精确数据的主要接口；`query-bindings.json` 只保留表格批量查询或上下文主题配置。
- `planner.py` 不再要求每个动态槽位都绑定 dataset；它只需收集 `metric_key` 和 `topic`，执行去重后的指标查询。
- `evidence_datasets`、`source_rules` 等内部兼容字段不应继续作为新模板的标注要求；待迁移模板完成后删除。
- `schoolDoubleHigh`、`hpm` 和数据库连接仍属于运行时/数据目录，不进入模板标注。

这种设计保留了精确指标的可追溯性，同时把大多数正文从“逐槽位取数”改成“先准备事实，再写作”。
