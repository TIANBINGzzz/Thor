## REQ-001：业务 Token 透传与按 MCP 注入

**要求**：Java 透传当前请求的业务 Token；Python 使用服务端维护的 MCP 规则表，仅向明确需要该凭据且本次获准使用的 MCP 注入。

### 必须满足

1. Java 从当前已认证请求/安全上下文获取业务 Token，完成业务授权后，按需通过内部字段 `credentials.platformBearer` 传给 Python；不换成共享账号，不接受正文中任意指定其他用户凭据。
2. 业务 Token、Java 签发的 Run JWT、模型供应商密钥是三类凭据；不得相互替代。Run JWT 用于授权 Python 执行请求，不能把业务 Token 嵌入 JWT 或模型输入。
3. Python 把业务 Token 当不透明凭据；除协议需要的 Header 前缀外，不改变其业务含义，不从中自行推导业务权限。业务权限由 Java 和下游业务服务校验。
4. 规则表由可信服务端配置维护，描述 MCP 标识、是否需要业务 Token、传输类型、目标 Header/环境变量及前缀；不保存 Token 值。初期可以是 Python 静态配置表，不要求新增数据库或配置服务。
5. 先按 Capability 的受控配置选择 MCP，再按规则注入。仅仅携带 Token 不得增加工具权限；前端、模型和普通业务输入不得覆盖 MCP 地址、凭据映射或接收方。
6. 需要凭据的 MCP 缺少 Token、未注册或注入配置无效时，必须在调用前失败；不需要业务 Token 的 MCP 不接收该 Token，也不因其缺失失败。
7. 注入仅作用于本次授权执行的 MCP 配置副本：HTTP/SSE 使用指定 Header；stdio 仅使用目标 MCP 子进程环境。不得修改全局 `os.environ`，也不得泄漏到其他 MCP 或 Run。
8. 并发请求、用户/租户切换和持久 Client 复用都必须隔离凭据。Token 更新、过期或撤销时不能继续冒用旧授权；正在执行和下一轮执行的处理规则须明确，不能默默复用旧配置。
9. 原始业务 Token 不得写入 Prompt、工具参数、会话记录、业务库、公共事件、私有观测或普通日志；错误信息、重试和审计也适用。运行内存及经授权的传输不等于可持久化保存。

### 验收检查

- 正向：业务 MCP 收到本次 Token，DB/DOCX 等未声明需要的 MCP 收不到；原配置与全局环境不变。
- 反向：缺少必需 Token、未知 MCP、伪造地址或映射均不能发起未授权调用；只传 Token 不能挂载额外 MCP。
- 隔离：两个用户并发、不同租户使用相同业务 ID、同会话下一轮更换 Token，均无串用；记录和错误出口中不存在原始凭据。

### 当前状态与待明确项

- **部分实现，2026-09-07 源码核对**：`python/runtime/mcp_auth.py` 的 `MCP_AUTH_RULES` 已有选择性注入、缺凭据失败和配置复制；`python/runtime/config.py` 用 `CCSDK_BUSINESS_MCP_CAPABILITIES` 控制业务 MCP 挂载。当前是代码内规则表，不是外部配置中心。
- `python/server.py` 与 `python/runtime/session_actor.py` 已用凭据相关指纹处理 Client 配置变化；协议、MCP 注入、Actor 更换存在对应测试。本文未执行这些测试，不据此声称真实链路已验收。
- Java 不在本仓库，本次未核对其真实透传链路；运行中 Token 到期/撤销、是否终止或要求重新授权，以及全部日志/持久化出口的泄漏回归仍需明确和验证。

## REQ-002：前端触发 Capability，执行资产保持内部化

**要求**：前端触发对象是可授权、可审计、可配置的业务能力 `Capability`。Workflow、Skill、Agent、模板和数据源是其内部组成，不是前端可自由选择的执行入口。

### 必须满足

1. 前端只提交服务端公布的可选capabilityRef和获准业务输入/会话/文件引用。2026-09-14用户确认普通会话省略能力，内部归一为conversation并照常授权；选择能力按当前消息生效。显示名不能把底层执行名称当任意指令。
2. Java 校验用户、租户、会话、文件和 Capability 权限；未经授权、未知或已停用的能力必须拒绝。前端隐藏按钮不能代替后端授权。
3. 可信服务端将 Capability 解析为内部执行配置。前端不得直接提交或通过嵌套字段、文本前缀覆盖 Workflow 名称、Skill 路径、Agent 配置、工具/MCP 地址、工作目录或权限。
4. Capability 标识与 Workflow 标识语义独立，不要求一一对应或字符串相等。同一 Workflow/Skill 可复用到多个能力；内部配置调整不应迫使前端改用另一个执行入口。
5. Java 负责业务能力注册和授权；Python 负责受控执行资产解析与装配。Java -> Python 可以传可信内部引用，但不能将浏览器提供的执行配置原样转发；具体注册信息放置和同步方式由接入方案明确。
6. 每次执行应能审计关联用户、租户、Capability、业务会话、Run、实际采用的配置和结果。配置可追溯方式可用受控版本或非秘密快照，不在本条预设新增 API 字段或业务表。
7. 固定流程优先组合“Capability + 可复用 Skill + 模板/数据源配置”。仅模板、数据源、业务口径或输出样式不同，不足以复制一个 Workflow；模板/数据源选择也须在授权范围内。
8. 只有流程拓扑、审批、并行、重试或外部副作用的编排语义确有不同，才考虑拆独立 Workflow，并记录差异与理由。Workflow 不是 Skill 或业务名称的另一种叫法。

### 验收检查

- 正向：用户选择已授权 Capability 即可执行，不需要知道内部 Skill、Workflow 或 Agent；同一内部流程可供多个能力配置复用。
- 反向：篡改 Capability、跨租户文件引用、注入 Workflow/Skill/Agent 字段或 `/workflow` 前缀都不能绕过业务授权与内部映射。
- 变更：仅替换模板/数据源时检查能否保持原 Workflow；拆流程时说明属于哪类编排语义差异，并能审计该 Run 实际执行的配置。
