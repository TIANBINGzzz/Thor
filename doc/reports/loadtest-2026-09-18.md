# ccagentsdk 部署与并发压测报告

测试日期：2026-09-18，主要采样时段北京时间 10:46–10:56。

## 结论

服务已部署至文档所在服务器，真实模型调用、JWT 鉴权和 SSE 均已验证。默认 **2 核 / 4 GiB 不适合 30 并发**：90 次请求失败 19 次，全部伴随 SDK 子进程被容器 OOM 杀死。提高至 **4 核 / 8 GiB** 后，同样的 30 并发测试 90/90 成功，内存峰值 5.60 GiB，但平均响应仍需 41.22 秒。这是短问答突发测试结果，不是生产容量承诺。

## 测试方法

- 通过服务器上的独立 Python 压测进程请求公开 HTTPS 入口，链路包含 Nginx、Runtime、SDK、真实模型；不包含 Java 和用户终端网络延迟。
- 每档并发同步发起一轮，等待整轮结束再进行下一轮，共三轮；档位间重启测试容器。不同并发槽使用不同业务会话，同一槽跨轮复用业务会话标识，但默认 query 模式不复用常驻 SDK Client。
- 能力为 `conversation`，省略 `payload`；输入固定为 `Compute 17 * 23. Reply only with the number. Do not use tools.`，预期答案为 `391`。
- 成功要求：创建 HTTP 202、SSE 返回 `run.completed`、完整答案去除首尾空白后等于 `391`。HTTP 接收成功不等于业务成功。
- 请求签发独立 JWT，读取 SSE 使用 `run.read`；客户端读取超时 360 秒，服务端执行超时使用默认 300 秒。无应用级失败重试。
- 每秒读取主机 `/proc` 和容器 cgroup 的 CPU、内存、PID、OOM 计数及磁盘空间。主机可用内存低于 1.5 GiB 或测试盘可用空间低于 512 MiB 时停止继续加压；实际未触发。
- 总耗时从客户端开始发送到 SSE 结束，包含失败请求；首字均值仅统计有文本的请求。P95 使用最近秩法。成功吞吐为成功请求数除以该档三轮总耗时，包含轮次等待。

## 判断与限制

- 少量普通问答可使用 2 核 / 4 GiB；本次 10 并发虽全部成功，但平均已接近 28 秒。不能据此承诺 4 GiB 可稳定支撑 30 并发。
- 4 核 / 8 GiB 可作为后续试运行起点；本次 30 并发内存约 5.60 GiB、CPU 接近 4 核上限，仍需业务排队、并发限制和延迟目标。该配置不能保证复杂任务或长期 30 并发。
- 扩容同时改变 CPU 和内存，消除了 OOM 并改善耗时；CPU 饱和及吞吐平台是瓶颈信号，但本测试没有将模型耗时与 SDK 启动耗时单独隔离。
- 完成请求上报的输入量约 2.15 万 Token/次，答案通常仅 2 个输出 Token；这些是 Runtime 上报值，不等于计费 Token。应另行核查默认上下文、工具规模及常驻 Client 模式的收益。
- 本次是固定短问答、每档三轮的同步突发测试；1/3 并发样本较少，P95 代表性有限。未覆盖长时间稳态、不同问题、数据库、文件上传、100 MB 文档、多版本存储、复杂工具调用或 Java 全链路。
- 服务器为共享主机，部署前已有 nginx/grafana 容器重启现象；资源统计包含这些背景负载。本次测试盘仅适合验证，大文件业务需另行规划容量与保留策略。
- 已验证：运行 157 项回归测试，155 项通过、2 项跳过；HTTPS 鉴权/真实模型/SSE 冒烟；独立 Docker 服务重启后容器自动恢复；文档地址仍为 HTTP 200。未进行整机重启验证。
- 工程要求：REQ-001 的业务 Token/MCP 透传本次不涉及；REQ-002 使用已登记 `conversation` 和绑定 Run JWT，未验证 Java 授权及生产多租户隔离，不能将压测结果视为这些要求已验收。
