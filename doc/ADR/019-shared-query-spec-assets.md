## 背景

用户确认将已知指标/数据集的查询固化，供问数及模板报告复用；不能只保存 SQL 字符串，也不能把不同数据库的值相互替代。

## 决策

- 在 `.claude/query-specs/<domain>/` 维护 JSON QuerySpec 与独立 SQL，描述来源、粒度、参数、口径、输出、前置条件和逐源验证。
- 模板引用查询标识；数据源连接和权限属于可信服务端，前端仍按原能力 payload 约定输入。查询标识不成为客户端执行入口。
- 已知定义优先使用资产；未命中但语义和授权已知时可动态生成只读 SQL。定义/历史期间不明时留空或问询，不编造查询。
- 本轮沉淀资产和验证，不改 Runtime、MCP 或 workflow 装配；运行时检索、驱动参数绑定与执行授权另行接入。

## 实现证据与差距

- [查询资产](../../.claude/query-specs/README.md)：23 条已定义、1 条报告源 SQL 待验证、8 项定义待补；18 问、12 张问数表、40 张报告表和15类段落来源规则均有覆盖记录。
- 验证：2026-09-14，23 条 MySQL 只读零行投影及输出列核验通过，3 项任务统计独立对照通过；13 项资产/合成数据测试通过。
- 差距：报告库未绑定；评分、成果计数和历史版本规则等保留待补。DBHub 不支持这些命名参数，不能把现有资产当作可直接执行工具。

## 后果

- 好处：问数、预制模板和上传范文可以复用同一业务定义，查询结果有明确来源。
- 代价：字段或口径变化时需同步资产版本、来源验证和模板引用。
- 风险：忽略前置条件、结果截断、NULL 或阶段/历史快照差异会产生错误报告，执行端仍需强制校验。
