## 背景

需求：学校的撰写和问答都要检索知识库，选型为 WeKnora。各校知识库互相隔离，共同的政策知识可以共享；校内不同业务使用不同的库，但不要求严格隔离。用户要求与供应商最低耦合，以后更换知识库时尽量只改代码和取值。

WeKnora 权限调研（源码核对）：
- 隔离单位是空间（tenant）。空间级 API Key 只属于一个空间，带其他空间的 `X-Tenant-ID` 返回 403；Key 的 `knowledge_base_ids` 为空表示本空间全部库可读。
- Key 按能力授权，`retrieve` 只能检索和读分块，`ingest` 才能写入。一个空间可以有多把 Key。
- 建 Key 要求空间 Owner 且只认 JWT。用普通用户 JWT 建空间会自动成为 Owner；用平台级 Key 建空间会跳过 Owner，之后没人能为该空间建 Key。
- 普通用户默认最多拥有 10 个空间，由 `WEKNORA_TENANT_MAX_OWNED_PER_USER` 调整，负数表示不限。新空间不带 Key，也不设置默认模型。

## 决策

- 部署形态：SaaS 多校共用一套 Runtime，按每轮业务 Token 解析的学校选择连接；本地部署一客户一套 Runtime。两种形态用同一套表，连接的学校字段都填具体 `tenantId` 或 `*`。
- 每校一个 WeKnora 空间，公共政策单独一个空间。WeKnora 只能逐空间创建，由自建的批量开通任务用一个专用普通账号的 JWT 逐校调用，并调大建空间配额；不用平台级 Key 建空间，不开跨空间超级用户。
- Runtime 每个空间只持有一把 `retrieve` Key，不设库白名单，授权边界即学校空间：同校用户共享校内全部知识，不宣称用途级或库级隔离。`ingest` Key 和开通账号归 Java 管理端，不进 Runtime 配置库。
- 检索由 Runtime 直接调用 WeKnora，不经 Java 代理；Java 负责认证和业务授权。WeKnora 只看到机器 Key，不知道 `userCode`，首期不按用户隔离，由 Run 记录用户、能力和实际检索的库与分块。
- 配置库新增四张与供应商无关的表：连接、用途、库、能力与用途的关联。能力绑定用途，不绑定具体库；学校归属记在连接上。详细字段和原因见[知识库接入契约](../specs/knowledge-base-connections.md)。
- 供应商差异只出现在适配器代码、连接的 `provider/credentials/config` 取值和库的 `external_id` 取值。模型只看到 `knowledge_search`、`knowledge_read` 两个工具和本 Run 内有效的引用编号；对话回答按编号标注依据，Runtime 推送含文档名、文档内位置和引用原文的快照，由 Java 随消息保存，历史出处不回查 WeKnora，规则见契约“引用与出处”。
- 未选：能力直接绑库，因为每校每能力都要一行，且新开学校要改能力；按校建 WeKnora 账号，因为开通和凭据管理成本随学校数增长；校内每个用途一把带白名单的 Key，作为敏感库的可选加固，不作默认。

## 后果与验证

- 换成同样是 Key 加库 ID 模式的知识库，只需新增适配器并改取值；需要逐用户凭据的供应商要重新设计凭据注入。
- 本校和公共政策在不同空间，至少两次调用；各空间分别取前 N 条交给模型综合，不跨空间比较分数。本地部署的公共政策可在本地 WeKnora 建空间同步或直连中心部署，只影响连接行取值。
- 已接受的差距：WeKnora v0.9.1 检索接口把完整查询文本写入日志（只清洗控制字符，不脱敏）。首期不做脱敏，查询原样发送，日志保留与访问控制按 WeKnora 部署运维管理。
- 运维验收：批量开通的重复提交幂等、超时后对账、开通账号保护与 Key 轮换。
- 引用精度随文件类型和解析器变化，无定位信息时只给文档名和原文；点开原文定位需服务端代理预览接口，不在首期。
- 尚未验证：平台级 Key 在目标空间内的实际权限、跨空间 403 的实测取证、检索质量及吞吐（WeKnora 检索接口无全局限流）。
