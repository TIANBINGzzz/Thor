# Worker 与 Client 预热优化实测摘要

核对日期：2026-10-15。本文记录本轮优化的原因、收益及验收边界；实现约束见[架构](../../ARCHITECTURE.md)、[配置字段](../../config/README.md)。

## 1. 测量口径

- 正文 TTFT：从发起请求到客户端收到第一段正文；不把 HTTP 响应头、SSE 状态、SDK 首消息或 thinking 当成正文。
- 分段基准：Runtime 装配 → Actor 排队 → Worker 领取/导入 → SDK 连接 → 本轮配置 → 模型 HTTP → 正文存储/SSE 返回。记录单调时钟、进程 CPU、池命中/重建原因及进程树内存。
- 本地 Windows、59 Linux、SDK 单层实验和完整 HTTP/SSE 的数据分开比较；真实模型与固定响应夹具分开。各阶段有包含关系，且各 scope 起点不同，不能直接相加或跨 scope 相减。
- 以下并发指不同业务会话；同会话仍由 Actor 串行。小样本中位数或单次测量均不代表容量、P95 或业务 SLA。

## 2. 优化经过

| 步骤 / 提交 | 发现与修改原因 | 修改及观测收益 | 结论边界 |
| --- | --- | --- | --- |
| ① Python Worker 池 / `d75a6a7` | 每个新会话都要启动 Python、导入模块，再连接 SDK；已有会话复用更快 | 提前准备未绑定身份的 Worker，空闲数 6、创建并发 2 均可配置。初轮本地真实 HTTP 测试：3 并发 TTFT 6.31→4.99 秒；6 并发 7.91→7.52 秒 | 只移走 Python 启动，SDK 尚未连接；6 并发收益小，不能据此宣称冷启动已解决 |
| ② 排查“关闭池反而慢约 2 秒” | 初次修改前 6 并发 7.91 秒，后来关池 9.93 秒，缺少同时期分段和资源记录 | 增补交错对照：旧/新关池各 24 请求，TTFT 9.38/9.72 秒；握手仅约 5–6 毫秒 | 没有复现固定 2 秒实现回退；不能把历史差值归因握手，也不能用不同批次直接证明代码无影响 |
| ③ 启动依赖与补池调度 / `c771ca9` | 无数据源的普通会话也提前导入 SQLAlchemy/SQL 解析器；后台补池可能与业务 SDK 初始化争抢 CPU/I/O | 数据依赖按需导入；已领取 Worker 连接 SDK 期间暂停新增后台导入。本地固定响应夹具、6 并发各 12 个首轮：关池导入 4.08→2.89 秒，Worker 就绪 7.82→6.87 秒，TTFT 9.26→8.77 秒 | 真模型另一组 6 并发 TTFT 9.85→9.94 秒，虽然 Worker 启动 6.23→6.02 秒；说明局部优化可能被模型波动抵消 |
| ④ 建立链路观测 / `448b1a6` | 只有总 TTFT 无法分清装配、启动、模型等待和流式缓冲 | 增加 Runtime/Actor/Worker 私有分段观测，配合模型 HTTP 透明代理与进程资源采样；59 装配约 13–32 毫秒、排队通常不足 2 毫秒，首次 Worker 可达 3.84 秒 | 观测本身不是提速；模型 HTTP 首字节仍不等于正文，不能把所有 SDK 等待算成 Python 执行 |
| ⑤ 随机工作区与收缩重建 / `e2b6241`、`1506d8a` | 预连接需要先固定 cwd；Token、模型或能力切换若总重建，会丢掉连接复用收益 | SQLite 原子绑定可信 `tenant + sub + businessSessionId` 与随机工作区；模型、规则、MCP/工具授权及凭据按轮更新，同一 MCP 实例受控 bind/清理；Token 不再进入连接固定指纹 | 该步没有独立 TTFT A/B，不能单列提速比例；目录、SDK 环境等不可热更项变化仍重建并 resume，故障/回收后仍需重连 |
| ⑥ 预连接 Client 池 / `1506d8a` | Worker 导入完成后仍需创建 CLI、SDK 握手及首轮初始化；仅 Worker 池无法消除 | 随机空白工作区先连接无业务身份/MCP 的 Client；授权后独占领取，绑定本轮配置再发消息。最终本地真实 HTTP 测试 3/6 并发首轮分别 3.02→1.22、4.30→1.55 秒 | 命中才有收益；已有历史恢复和固定配置不匹配走冷启动。预热不消除模型推理及下游工具耗时 |
| ⑦ 59 部署启用及复测 | 新代码部署后仍需核对有效配置、池 ready、命中和内存，不能只看镜像标签 | 开启 6 个空闲 Client 后，公网首轮 6.43→2.89 秒，约降 55%；日志确认 `source=prewarmed`，新会话 Worker 启动计时为 0 | 前后小样本，非受控 A/B；仍有复用轮 7.51 秒和公网早期事件延迟，不能宣布全链路长尾消失 |

## 3. Client 池设计与本地对照

空白 Client 预连接 → 已授权新会话领取 → 原子绑定工作区 → 装配获准 MCP/规则/凭据 → 执行；领取后专属原会话，不跨用户归还空白池，后台补新 Client。现有会话优先复用；恢复历史单独处理。

容量分为 `max_idle`、`max_starting`、`max_live`，另设 `min_available_memory_mib`；池容量不是并发上限。随机目录只解决提前分配与稳定恢复，不构成多租户沙箱。

| 实验范围 | 并发 / 每组首轮样本数 | 修改前或冷连接 TTFT 中位数 | 预连接命中后 | 收益 |
| --- | --- | --- | --- | --- |
| 本地 SDK 单层、真实模型实验 | 3 / 9 | 2.924 秒 | 2.103 秒 | 降约 28% |
| 本地 SDK 单层、真实模型实验 | 6 / 18 | 3.994 秒 | 2.279 秒 | 降约 43% |
| 最终实现、本地真实模型 HTTP/SSE，前第 2 / 后第 3 批 | 3 / 3 | 3.020 秒 | 1.225 秒 | 降约 59%；热轮 0.231/0.295 秒 |
| 最终实现、本地真实模型 HTTP/SSE，前后第 3 批 | 6 / 6 | 4.296 秒 | 1.545 秒 | 降约 64%；热轮 0.515/0.507 秒 |

保留反例：最终实现第 2 批 3 并发 TTFT 为 7.371 秒，当时池统计为 0 命中/3 未命中；后续第 3 批为 3/3 命中，6 并发为 6/6 命中。该反例证明不能只看 `max_idle=6`，还须看请求到达时是否 ready、配置是否匹配；当前记录不足以单凭结果确定那次未命中的唯一原因。

## 4. 59 的分段证据与上线收益

同容器内独立临时 Runtime、同一真实模型的关池/开池各首轮对照如下。开池为 1 个预连接 Client，区别于后续生产配置 6 个。

| 阶段 | 关池首轮 | 命中预连接首轮 | 发现 |
| --- | --- | --- | --- |
| Runtime 装配 / Actor 排队 | 32 / 0.50 毫秒 | 20 / 1.23 毫秒 | 不是这次秒级延迟主因 |
| prepared → Worker ready | 3,841 毫秒 | 0.60 毫秒 | 约 3.8 秒启动移到请求之前 |
| Python 导入 / SDK 连接 | 2,010 / 1,118 毫秒 | 提前完成 | 导入 CPU 约 1,941 毫秒，确有计算成本；多进程并发仍争用资源 |
| 绑定 → query_begin | 743 毫秒 | 592 毫秒 | 近似本轮配置耗时，非完整独立配置埋点 |
| 主模型 HTTP 发出，相对请求开始 | 4,804 毫秒 | 762 毫秒 | 预热让请求更早抵达模型 |
| 模型响应头等待 | 4,974 毫秒 | 1,585 毫秒 | 两次模型等待不同，不能全部算成池收益 |
| 正文 TTFT | 10.074 秒 | 3.666 秒 | 确定省掉启动；总差值 6.41 秒不全来自启动 |

正文落库到 SSE yield 约 0.2–0.4 毫秒。命中预热首轮从模型首字节到正文仍约 1.3 秒，说明连接就绪后还可能经历 thinking 等非正文阶段。

2026-10-15 生产配置调整前后，使用相同简单算术题、各路径独立会话，顺序发送三轮，均完成成功：

| 路径与配置 | 首轮 TTFT | 同会话第 2 轮 | 同会话第 3 轮 |
| --- | --- | --- | --- |
| 公网，关池 | 6.43 秒 | 1.31 秒 | 1.86 秒 |
| 公网，开池 6 | 2.887 秒 | 1.710 秒 | 1.546 秒 |
| 直连 Java，关池 | 6.51 秒 | 1.62 秒 | 1.36 秒 |
| 直连 Java，开池 6 | 3.478 秒 | 7.507 秒 | 1.620 秒 |

复测有效配置：空闲 6、同时创建 2、总存活上限 24、可用内存保护阈值 1,024 MiB。测前 ready=6，测后补回 6；池累计 hits=3、misses=0、failures=0，包含本测试之外的会话，不能都算作本次请求。

## 5. 代价、能力核验及未解决项

- **内存**：59 当前空白进程组 PSS 约 213–230 MiB，绑定组约 267–272 MiB；6 空闲+3 绑定合计约 2,104 MiB。可用内存由测前 1,913 降至测后 1,166 MiB，接近保护阈值；CPU 约 91–93% idle、未观测到活跃换页。保留池 6，暂无证据支持继续加大，也不能将上限 24 视为已验收容量。
- **模型/SDK 长尾**：7.507 秒的复用轮没有重建，Python RunStore 首正文约 7.44 秒；另一次长答约 236 秒后成功，但未开完整 trace，不能区分模型、网络或 SDK 重试。预热池解决启动成本，不解决所有长尾。
- **公网流式**：直连 Java 约 50–74 毫秒收到 stream_meta，公网短答常到正文时才收到早期事件；定位在框架网关之前的代理段，具体配置未确定。Java 另发现先 flush、后设置 SSE Content-Type 的响应顺序问题，尚未修改验收；不能据此解释所有缓冲。长答能逐块返回，不能说公网完全不流式。
- **能力切换**：本地真实执行的双高问数与独立只读 SQL 基准一致；同会话切换撰写、生图成功，DOCX 包及正文检查通过，PNG 为 1024×1024；两类成果各有 1 次 artifact.ready，存储状态 ready 且有 fileId。校园能力缺业务 Token 时以 MCPAuthError 拒绝。上述不等于 59 全能力、网页回显、DOCX 视觉质量或真实校园授权验收通过。
