## 背景

用户需要从大量候选项中选择对象，将完整候选集放入模型上下文会增加无关 Token 消耗。

## 决策

- 使用 `@type:value` 引用；候选集保留在服务端，前端通过 `/api/options` 分页搜索，默认 20 条、上限 50 条。
- 服务端在注入上下文前重新解析并核对引用，只提供命中对象的描述；不存在或未知类型须明确标识，不采信前端标签。

## 实现证据与差距

- 范围与代码：[references.py](../../python/local/references.py) 的 `search_source`、`reference_prompt_context` 及 [ChatWorkspace.tsx](../../web/app/components/ChatWorkspace.tsx) 引用选择器。
- 验证：[test_references.py](../../python/tests/test_references.py) 的分页上限、去重、中文标点、编码和无效引用检查随本次 Python 测试通过。
- 差距：前端交互与十万级数据性能本次未验收；当前候选集来自本地扫描，不代表生产资源 ACL。

## 后果

- 好处：模型上下文随所选对象增长，而不是随候选集规模增长。
- 代价：需维护引用解析器、选择器、数据源和特殊字符编码。
- 风险：新增数据源必须补充服务端复核；本地路径校验不等于租户授权。
