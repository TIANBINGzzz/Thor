# 架构决策记录（ADR）

本目录记录项目的重要架构决策。ADR 是决策历史，不是实现任务清单；代码删除或重构不等于删除对应的 ADR。

## 什么时候写 ADR

- 技术栈选型（MCP vs ORM、容器 vs 沙箱）
- 安全边界设计（权限隔离、认证方式）
- 数据流向和存储方式（引用语法、会话文件）
- 明确放弃某个方案（为什么不用 XX）

## 什么时候不写 ADR

- 实现细节（某个函数怎么写）
- 临时决策（先这样，以后再改）
- 能从代码推导的事实（目录结构、依赖版本）

## 状态模型

决策状态和实现状态必须分别填写，不能用“已完成”同时表示两者：

### 决策状态

- `提议`：正在讨论，尚未作为架构依据。
- `已采纳`：已经批准，作为当前架构依据；不代表代码已经完成。
- `已替代`：已由新的 ADR 取代，保留本文档用于追溯。
- `已废弃`：不再适用，且暂时没有明确替代方案。
- `已拒绝`：评估过但明确不采用，保留原因以避免重复讨论。

### 实现状态

- `未开始`：没有可验收的实现。
- `进行中`：已经开始开发，但尚未形成可用闭环。
- `部分实现`：部分路径可用，仍有明确缺口。
- `已实现`：代码、配置、测试或验收证据已覆盖决策的主要范围。
- `不适用`：该 ADR 是原则、提议或历史记录，不要求当前代码实现。

典型组合是：`已采纳 + 未开始`（决策已定但还没开发）、`已采纳 + 部分实现`（当前 CCSDK 接入状态）、`已替代 + 不适用`（历史方案）。

`已删除`不是决策状态，而是极少使用的文档处置结果，只能出现在索引中的墓碑记录；它不表示决策被撤销。

生命周期可以简化为：`提议 → 已采纳 → 已替代/已废弃/已拒绝`；实现进度独立沿着 `未开始 → 进行中 → 部分实现 → 已实现` 演进。

## ADR 生命周期与删除规则

1. 先以 `提议 + 未开始` 创建 ADR；评审通过后改为 `已采纳`。
2. 实现过程中只更新“实现状态”，不把“已实现”写入决策状态。
3. 方案发生变化时，新建 ADR，并在旧 ADR 中填写 `决策状态: 已替代`、`替代: ADR-XXX`；新 ADR 的“被替代”列反向记录旧编号。
4. 没有替代方案但不再适用时，标记 `已废弃` 并写明原因和日期。
5. 明确不采用的方案标记 `已拒绝`，保留评估结论。
6. 未进入索引的草稿、重复文件或误提交文件可以直接删除；已经进入索引、被引用、已采纳、已拒绝、已废弃或已替代的 ADR 默认不删除，只改变状态。
7. 若确需物理删除已归档 ADR（例如误提交、合规清理），必须先在索引中保留不带链接的编号、标题、“已删除”、原因、日期和替代编号，并确认没有断开的文档链接；Git 历史仍是唯一恢复来源。
8. 既有 ADR 只需补齐当前元数据，不强制伪造过去的状态变更；从本次规范启用后发生的变更写入“状态变更记录”。
