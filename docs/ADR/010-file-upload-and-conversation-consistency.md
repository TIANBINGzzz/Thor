# ADR-010: 文件上传与文件对话一致性

日期: 2026-08-17  
决策状态: 已采纳
实现状态: 部分实现
替代: 无
被替代: 无

## 背景

文件上传、文件引用和文件预览分别经过前端、Web 代理和 Agent 服务，原实现存在状态不同步：
上传失败仍可能发送消息，项目文件引用被当作未知类型，模型生成的会话文件也不会进入后续上下文。
流式聊天还存在连接误判和历史落盘时机过晚的问题，导致处理中文件时界面停滞，刷新后只剩文件。

## 决策

1. 文件先进入待上传列表，发送时统一上传；任一文件失败则不发送消息。
2. 服务端按本次请求实际新增的文件返回记录，会话上下文合并上传文件和会话目录产物。
3. 增加 `@file:` 数据源，服务端重新校验项目路径、文件存在性和大小后再注入模型上下文。
4. 下载接口继续按附件响应；前端对图片和 PDF 使用 Blob URL 预览，避免不可信内容直接执行。
5. SSE 仅在真实断开时中止 Agent；对话 turn 先落盘并在流式过程中更新，文档类请求明确要求最终交付有效 `.docx`。

## 后果

### 好处

- 上传状态、会话文件清单和模型上下文使用同一份文件事实。
- 文件引用可搜索、可校验，失败不会静默变成错误对话。
- 预览和下载保持清晰的安全边界。
- 长时间工具调用能持续显示进度，刷新可恢复已持久化的用户消息和 assistant 事件。

### 代价

- 前端需要维护待上传队列和上传中的发送状态。
- 二进制预览需要管理 Blob URL 的释放。
- 流式事件会产生有限的周期性会话写入开销。

### 风险

- 大文件上传仍会占用发送前的等待时间。
- `@file:` 目录清单使用短缓存，刚创建的项目文件可能稍后才出现在候选项中。
